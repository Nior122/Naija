## 1. What the creation key is today

- The client generates 32 random bytes with Godot `Crypto.generate_random_bytes` and stores them as 64 hex characters in `user://naija-multiplayer.cfg` (`multiplayer_client.gd`, `_load_local_session`, ~276–286). The file is plaintext, as documented.
- Each `identity.create` sends the key. The server validates it as 64 hex characters and stores only its unsalted SHA-256 (`creationKeyHash`). The key itself is not written to state.
- If the hash matches no player, the server **creates** a character and returns a session token. Each socket may create one identity (code reading: `identityCreated`).
- If the hash matches an existing player, the server **recovers** that player: it rotates the session token and deletes the old token hash (code reading, `createIdentity` ~871–890). It refuses only when that player's socket is currently open (`player_already_connected`).
- The session token is what later `session.resume` calls use. It has no expiry and no revocation.

So the creation key is **a reusable, non-expiring recovery credential**, not a one-time enrollment code. Presenting it again takes over the character, and rotating the token is how the takeover happens.

## 2. Threat model

| Actor | Capability | Impact |
|---|---|---|
| Holder of a leaked key (from a client's plaintext cfg, a backup, a screenshot, a support log) | Presents the key from any socket | Takes over the character whenever it is offline. Locks out the real player by rotating the token. |
| Unauthenticated network attacker on plaintext transport | Reads the key and token on the wire | Same as above. The server has no TLS (`docs/SECURITY_PLAN.md`); this depends on a WSS proxy that is not verified. |
| Anonymous client that creates many identities | Opens sockets, sends `identity.create` with random keys | Fills world state. Each new identity costs about 22 KB in the saved file. See E8. |
| Concurrent clients with the same new key (a bug, a retry storm, or a deliberate race) | Two sockets send the same key at once | Two sockets both receive `identity.created` for one player. One token is then silently invalid. See E3. |
| Server operator / backup reader | Reads `creationKeyHash` and `tokenHash` | Unsalted SHA-256 of a 256-bit random key is not practically reversible. Low risk for keys generated by the official client. A weaker key (for example, a custom client) would be guessable. |

## 3. Verified findings (experiment, all on temporary state)

| # | Scenario | Result | Meaning |
|---|---|---|---|
| E1 | Create with key K on socket A. Close. Present K on socket B (recovery). Resume with A's original token. | Same `playerId`. Token rotated. Old token → `session_invalid`. | **Confirmed.** Possessing the key takes over the character and invalidates the previous session. |
| E2 | Create with K, resume on socket A (online). Present K on socket B. | `player_already_connected` | **Confirmed.** Takeover is refused only while the player is online. |
| E3 | Two sockets send the **same new** key back to back. | Both receive `identity.created` with the **same `playerId`** and different tokens. A's token then returns `session_invalid`. One player record in state. | **Confirmed race.** Code reading: the second request takes the recovery path before the first socket is attached, so the player is not yet treated as "online". The losing socket is told it succeeded but has no working token. |
| E4 | 30 `identity.create` messages with an invalid key, sent in a burst. | 2 × `invalid_creation_key`, 28 × `rate_limited`. Socket stayed open. | The burst was limited by a rate limit. The experiment did not separate the per-socket command limit (20 per 10 s) from the pending-create guard. |
| E4b | 8 invalid keys, one every 150 ms. | 8 × `invalid_creation_key`. Socket stayed open. | **Confirmed.** Invalid-key errors do not count toward the 5-message disconnect (they are sent with `sendError`, not `invalid()`). Only the per-socket command limit bounds this. Not tested beyond 8 paced messages. |
| E5 | 36 sockets opened from 127.0.0.1 within a minute, each creating an identity. | 30 identities created. 6 sockets closed with code 1008 (connection rate limit). | **Confirmed.** About 30 new identities per minute per IP at default settings. Attackers behind many IPs are not bounded by this. |
| E6 / E6b | Make the next save fail (replace the state directory with a file) and send a create. Then restore and create one more identity. | The failed create returns `persistence_failed`. After the next successful save, the file holds **1 household with no player** and extra people and families. Counts before the failure: 1 player, 3 people, 1 household, 1 family. After the next save: 2 players, 8 people, 3 households, 3 families. | **Confirmed orphaned records.** The rollback removes only the player and map entries (`world-engine.ts` ~959–966). The family, household, and people from `createStarterFamily` persist and are saved with the next successful write. |
| E7 | Ten identities in sequence. | About 22.5 KB added per identity (125 KB after one; 328 KB after ten). | Measured growth per identity. |
| E8 | Keep creating identities until the save fails. | Save failed at **629** identities in the final run (653 in an earlier run; file about 16.0 MB). The next create returned `persistence_failed`. **Shutdown then threw** `World data file exceeds the 16 MiB prototype limit.` (uncaught in the experiment's shutdown call). | **Confirmed availability risk.** Anyone who can create identities can fill the state file, after which saves fail. Shutdown behaviour at the cap was not examined further (see section 5, R7). The effect on existing players after the cap was not tested. |

Each row was run once on a fresh server instance (per-instance limits reset). Numbers vary by a few percent between runs because the keys are random and the starter family size varies.

## 4. Code-reading findings (not run as separate experiments)

- **Keys never expire and cannot be revoked.** There is no rotation, no key version, and no admin path to invalidate a key.
- **Tokens never expire.** A resumed token is only rotated by a key-based recovery. A stolen token works until the next recovery.
- **`session.resume` uses only the token** (shape `/^[A-Za-z0-9_-]{40,64}$/` plus a hash lookup). There is no key-based check on resume.
- **The client does not check the stored key's format.** `_load_local_session` keeps any key of 32 or more characters. A non-hex key of 32+ characters would be kept and rejected forever. The client has no handler for `invalid_creation_key`.
- **The `session_invalid` fallback resends the stored key** as `identity.create` (`multiplayer_client.gd` ~221–227). The key therefore doubles as the client's own recovery credential. This is current behaviour and was not invented here.
- **Server-side key entropy is not checked.** Any 64-hex value is accepted. Keys from the official client are 256-bit random. A custom client can register a guessable key, and a guessable key is a takeover target for anyone who guesses it.
- **Limits** (defaults, `world-engine.ts` 235–245, 528–558): 8 KiB per message; 5 invalid messages before disconnect (`invalid()` only); 30 connection attempts per minute per IP; 64 sockets; 20 commands per 10 s per socket; 50,000 persisted players; 16 MiB state file.
- **`SECURITY_PLAN.md` says the server "rejects a second active connection".** That is true only while the player is online (E2). It does not protect an offline character (E1).

## 5. Remediation options (none implemented)

Each option says whether it changes the client and whether it is backward-compatible. Options marked **server-only** can be implemented without a client release.

| ID | Change | Client change? | Backward-compatible? | Notes |
|---|---|---|---|---|
| R1 | **Reserve the key during creation.** Treat a player as "connected" from creation until its creating socket closes, and reject a second create for the same new key while the first is pending (return `identity_creation_pending` or `player_already_connected`). Keep the same-socket retry path (idempotent). | No | Yes | Fixes E3. Must be tested with the existing retry test (`app.test.mjs` ~610–637) and a new concurrency test. |
| R2 | **Roll back all records on a failed save.** Snapshot the family, household, and people maps before `createStarterFamily`, and restore them on failure as well as the player and map entries. | No | Yes (no stored-data change) | Fixes E6. Test: E6b must show 0 orphaned records. |
| R3 | **Count `invalid_creation_key` toward the invalid-message disconnect** (or add its own small limit). | No | Yes, but a legitimate client that sends many invalid keys is affected. Check the client first. | Fixes E4b. Low priority. |
| R4 | **Identity creation budget.** Add a per-IP and global budget for new identities (per hour or per day), and a clear error when it is hit. Choose values with the operator. | No | Yes | Limits E5 and the growth in E7. Does not solve distributed abuse. |
| R5 | **State-cap policy.** Decide what happens near 16 MiB: raise the cap with a measured budget, move identity creation behind an operator-issued invite, or add a retention policy for never-resumed identities. A retention policy deletes data and needs an explicit product and legal decision. | No | Depends | Fixes the availability part of E8. Must not be done silently. Shutdown at the cap (`shutdown_error` in E8) should be made to fail with a logged, non-crashing error, and this needs a test. |
| R6 | **Key-hash hardening.** Keep existing unsalted hashes readable. On a successful presentation, store an HMAC-SHA-256 of the key with a server secret loaded from the environment (no default). Accept both forms during a transition, then drop the old form. | No | Yes, with a migration | Needs a server secret that must be kept and backed up. Losing the secret would lock out every player. Not needed for 256-bit random keys, so this is optional. |
| R7 | **Key or token rotation and revocation.** Let the client receive a new key on each successful recovery, and let the server expire tokens after inactivity. | **Yes** | Only with a deprecation window and tests on both sides | Needs a client change. Not invented here. Should be a separate reviewed release. |
| R8 | **Stop recovery by key alone.** Require the existing token (or a second factor) for recovery, and keep key-based recovery only for a documented migration window. | **Yes** | Not without a migration plan | This is the strongest fix, and it changes the current `session_invalid` fallback. Requires user approval. |
| R9 | **Client validation.** Validate the stored key as 64 hex characters before use, regenerate otherwise, and handle `invalid_creation_key`. | Yes (small) | Yes | Does not change server behaviour. Needs a Godot test run, which was not done here. |
| R10 | **Require TLS in production.** Refuse to start in production without a documented WSS-terminating proxy, or add a check that the server sees `x-forwarded-proto: https` when trusted. | No | Deployment change | The server has no TLS. This is a deployment control, not verified. |

## 6. Recommended order (for user decision)

1. **Server-only, no client change:** R1 (concurrency), R2 (rollback), with tests. These fix two confirmed bugs. They do not change how keys work.
2. **Decision needed:** R4/R5 (identity budget and cap policy). These are product and operations decisions.
3. **Decision needed:** R8 (stop key-only recovery) and R7 (rotation). These change authentication and need a migration plan and a client release. Do not implement without approval.
4. **Deployment:** R10 (TLS) and R9 (client validation).

No option in this review has been implemented. Nothing in the repository changed behaviour.

## 7. Test coverage gaps (current)

Present: retry recovery (same player, new token, resume works, one player record, key absent from state) in `test/app.test.mjs` ~610–637.

Not covered: old-token rejection after rotation (E1); offline takeover; second socket while online (E2); concurrent same-key creation (E3); invalid key format and its counting (E4, E4b); identity-create rate limiting (E5); flush-failure rollback of families, households, and people (E6); uniqueness of `creationKeyHash` and `tokenHash` on load; cap behaviour and shutdown at cap (E8).

## 8. Limitations

- The experiment ran on loopback, one process, with the default limits. It is not a load test.
- No behaviour was verified against a deployed or TLS-terminated server.
- The client's key generation (Godot `Crypto`) was read from source. Godot was not run here.
- The 22 KB per-identity figure is measured on this code and seed data, and will change with content.
- "Impact on existing players after the cap" (E8) was not tested.
- This review does not claim the system is secure or ready for launch.
