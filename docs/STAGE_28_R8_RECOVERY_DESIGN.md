## 1. Current behaviour (verified in this phase unless marked)

| Fact | Evidence |
|---|---|
| A creation key is a 64-hex-character value generated by the client. It is the only recovery credential. | Creation-key review, section 1 |
| The server stores `creationKeyHash` as an **unsalted SHA-256** of the key. | `world-engine.ts` (`createIdentity`); review section 4 |
| Presenting a valid key **rotates the session token**. The previous token then returns `session_invalid`. | Experiment E1 (`/tmp/s28/creation-key-experiment.json`) |
| A key that matches an **offline** identity takes that identity over. A key that matches an **online** identity is refused with `player_already_connected`. | E2; `recoverIdentity` |
| Keys never expire and cannot be revoked or rotated. A key can be presented any number of times. | Review section 4 |
| Two requests with the same key that race for a **new** identity now produce one identity. Concurrent recovery of an existing identity is also serialized (R1 fix, tests in `test/identity-concurrency.test.mjs`). | R1 tests, this phase |
| The session token is stored server-side as a hash (`tokenHash`). Tokens have no expiry. | `world-engine.ts` |

**Consequence (the core risk).** Anyone who obtains a creation key can take over the identity it belongs to, while that identity is offline, and the real player loses their session. The key is therefore a full bearer credential for the character. Keys are also stored by the client (`multiplayer_client.gd`), so any copy of client storage, a log, or a screenshot of a key is a takeover credential.

## 2. Threat model for recovery

| Actor / event | What they gain today | Desired outcome |
|---|---|---|
| Player who lost the device | Recovers with the key (works) | Keep working through a documented path |
| Attacker who copied the key from client storage | Takes over the character | Blocked or made detectable |
| Attacker with a stolen unlocked device | Same as the player | Limited by session timeout and notification (future) |
| Two devices with the same key | Last recovery wins; the other session is cut | Defined, visible behaviour |
| Server operator | Can read hashes only (unsalted, so a leaked database allows offline lookup of guessable keys only; keys are 256-bit random, so guessing is not the practical risk) | Break-glass use is audited |

The practical risk is **copying of a valid key**, not guessing. A 256-bit random key cannot be guessed. Salting or HMAC (R6) therefore reduces the damage of a database leak but does not stop a copied key. Only a second factor, a device-bound secret, or a recovery code that is rotated on use changes the takeover risk.

## 3. Options considered

| Option | What it does | Strengths | Weaknesses / dependencies |
|---|---|---|---|
| **A. Account-bound recovery** | Recovery requires a signed-in account that owns the identity | Standard model; supports notification and revocation | Depends on the production account system (separate task). Not available now. |
| **B. Device-bound session + key only for a documented window** | Keep the key for lost-device recovery, but refuse takeover of an identity whose device still holds a valid session. Add a recovery grant with a waiting period. | Closes the easy copy-and-take-over case; no account needed | The waiting period needs a notification channel that does not exist yet. Client change needed. |
| **C. One-time recovery code, rotated on every use** | At creation, the server issues a recovery code (shown once to the player). It is hashed (salted) and replaced on each successful recovery. | Each code works once, so a copied code is detected when the player next recovers | Client must display and store the code. Lost code plus lost device is still unrecoverable without an operator procedure. |
| **D. Operator-assisted reissue (break-glass)** | An operator reissues a key for an identity after an out-of-band check, with an audit record | Covers true lockout | Manual, not scalable. Needs a written procedure and an audit log. Never automatic. |

**Recommended direction (for review, not decided):** B now, as the server-side policy, with C as the medium-term client feature, A when accounts exist, and D as a documented fallback. The decision is a product decision (see section 9).

## 4. Required design elements

### 4.1 Existing players and credentials (compatibility)

- Every existing identity has an **unsalted** `creationKeyHash`. The first version of R8 must keep accepting these hashes.
- **Lazy upgrade only:** on a successful presentation of the key, the server may store a salted or HMAC form (R6) alongside the old one. No bulk rewrite of saved worlds. A bulk migration needs a reviewed plan and a dry run on a copy (no live player data is touched by tests).
- Identities whose keys are never presented keep the old form. The number of such identities must be reported (a count query on saved data), not assumed.
- Existing session tokens remain valid until rotated or expired. Expiry is new behaviour and needs a deprecation window (R7).

### 4.2 Lost-device recovery

- The player presents the key (Option B) or a current recovery code (Option C) from a new device.
- The server rotates the session token (existing behaviour) and records the recovery time and source (IP is already logged; no new personal data should be added without review).
- If the player has neither the key nor a code, recovery is impossible without the operator procedure (D). This must be stated to players. It is not hidden.

### 4.3 Secure ownership verification

- Compare hashes with a constant-time comparison (`timingSafeEqual`) on the hashed values, never on raw keys.
- Never echo the key, a token, or a hash in an error, log line, metric, or report. Current errors use fixed text; keep it that way.
- Keep per-IP and per-socket limits (existing). Add a per-identity failed-recovery counter only after review, because a counter can be abused to lock a player out (see 4.9).

### 4.4 Revocation

- Each identity needs a **key version** (or recovery-code version). Revoking the key increments the version and invalidates the old value.
- Revocation requires authority: the player (with a valid session) or an operator (procedure D). It must not be possible to revoke someone else's key with a copied key alone, or revocation becomes a new takeover vector.
- The revoked value must stop working at once in the authoritative state, not only in the client.

### 4.5 Concurrent recovery

- Same-key requests are serialized by the R1 reservation (in-process). Multi-process deployments are **not** covered by that reservation. Multi-process fencing is covered only by the database version check in the PostgreSQL store, and its tests are separate. Do not claim cross-process exactly-once behaviour.
- Policy when two devices recover at once: one wins, the other receives `identity_creation_in_progress` (or a new code, to be defined) and must retry. The retry then reports `session_invalid` or succeeds, depending on order. The client must handle both.

### 4.6 Session invalidation

- Recovery invalidates the previous session token (existing).
- Revocation invalidates the session token and any socket bound to it.
- Session expiry (inactivity) is not implemented. It is a separate design item in R7.
- A session in use on a socket when the token rotates must be closed with a defined code. Check that the current behaviour (a takeover is blocked only while the player is online) is documented in `docs/SECURITY_PLAN.md` once this design is approved.

### 4.7 Failure and rollback

- A recovery that cannot be saved is rolled back in memory (existing code restores the old token hash). Keep this, and keep tests that fail the save at the token-rotation point.
- A recovery whose response is lost after a successful save leaves the new token in the authoritative state. The client never received it. The next recovery with the same key rotates it again. This is safe but must be documented for the client team (see R7, scenario 2).

### 4.8 Avoiding permanent lockout

- No automatic lockout on failed attempts. A lockout rule would let an attacker lock out real players.
- Lost key and lost device: break-glass reissue (D) with a written procedure, identity verification outside the game, an audit record, and no bulk actions.
- No deletion or pruning as part of recovery (see the directive on automatic pruning).

### 4.9 Abuse controls

- Rate limits on recovery attempts (per IP, per socket, and per identity) must not reveal whether an identity exists. Responses for an unknown key and a wrong key should be the same. (Current behaviour: an unknown key creates a new identity; that is a separate issue, R4 in the review.)

## 6. Migration compatibility

1. Phase 0 (current): no change.
2. Phase 1: server accepts old and new forms; lazy upgrade on successful presentation; metrics for unmigrated count. No client change.
3. Phase 2: client release that stores the recovery code (Option C) or the new key version; server keeps old form accepted for a documented window.
4. Phase 3: end of window, after the unmigrated count is reviewed. Any removal of the old form is a separate approved change.

Each phase needs tests that run against a copy of a saved world, and a rollback plan.

## 8. What this design does not claim

- It does not claim that a stolen key can be detected today.
- It does not claim that the current game is safe for real players. Transport security (R10) and the account system are separate.
- It does not claim exactly-once behaviour across processes.

## 10. Option B: required detail before implementation (design only)

> **Update (2026-10-10):** Section 11 records the adopted direction for review. Where section 11 differs from this section (notably D3 and D4, and the channel), section 11 governs. Section 10 remains as the analysis it was.

This section answers the four points the user asked for before any code is written: how ownership is verified, how notifications are delivered, how the legitimate player cancels, and what happens when delivery or processing fails. Existing players keep access. Recovery is never silently allowed when notification fails. **Nothing here is implemented.**

### 10.1 What "a valid device session" means (verification)

- The session token is a random 32-byte value held by the device's client storage. The server stores only `tokenHash` (SHA-256). A session is **live** when the identity's socket is connected (the `online` map). A live session is what the server can verify today without new state.
- **Proposed rule (D1):** an identity has a valid device session when a session token for it is presented on a connected socket. A key-only takeover is refused while that is true (the current `player_already_connected` behaviour, extended to the new flow).
- **Not decided (D2):** whether a token that was used recently, but whose socket is now closed, also counts as valid. A window would need a constant (for example, "last used within N days"). No value is proposed here, because any value would be invented. Without a window, tokens never expire, so the owner of an offline identity would be treated as having a valid session forever. That would make key-only recovery unreachable. D2 must be answered before implementation.
- Ownership of a recovery is shown by **possession of the current session token**, not by the key. A key-only holder cannot cancel a pending recovery or pass the session check.

### 10.2 Recovery request and waiting period

1. A key-only request for an identity with **no** valid device session does **not** rotate the token. It creates a **pending recovery** record in the saved world: `playerId`, `requestedAt` (server time), and the requested key version. It stores **no IP address and no requester identifier**.
2. The pending record is saved in the same serialized commit as the request. If that save fails, the request is refused and nothing changes (fail closed).
3. The token rotates only when the waiting period has passed and the completion check (10.5) succeeds. Default waiting period: **24 hours** (user proposal). Configurable through an environment variable (name and bounds to be set with the implementation; proposed 1–168 hours). The period is measured from `requestedAt` in server time.
4. A second key-only request while one is pending does **not** restart the clock. This stops repeated requests from extending the period indefinitely, and it stops an attacker from pushing back the owner's cancel window.
5. While a recovery is pending, the **current token keeps working**. The owner's access is therefore unchanged during the wait.

### 10.3 Notification delivery

- **There is no out-of-band channel today.** The game has no email, SMS, push, or account contact details. The only channel is the game socket, and an offline owner has no socket.
- **What can be delivered now:** the pending-recovery notice is sent to any connected socket of the identity, and it is shown on the owner's next `session.resume` with the valid token. The server records `notifiedAt` when the notice is actually sent to a socket. The server does not treat a send as confirmed delivery to a person.
- **Consequence (decision D3):** a lost-device owner will not be notified until they next log in. An attacker can therefore wait out the 24 hours without any alert reaching the owner. The waiting period protects only owners who log in during that time. This is a real limit, and it must be accepted or rejected explicitly.
- **Strict reading of "do not permit recovery when notification fails":** completion would require `notifiedAt` to be set, which needs a connected owner. Lost-device owners could then never recover without an operator (break-glass, D). That is a safe outcome, but it removes self-service recovery for lost devices. This is the main product decision (D4).

### 10.4 Cancelling as the legitimate player

- **Automatic cancel:** a successful `session.resume` with the valid token cancels any pending recovery for that identity in the same serialized commit. The owner needs to do nothing beyond signing in.
- **Explicit cancel:** `identity.recovery.cancel` with the session token. It is refused without the token. The key alone cannot cancel.
- Cancel and completion run in the serialized queue. Whichever commits first wins. Completion re-checks, inside the queue, that the pending record still exists and that the wait has passed. A cancel that commits after completion has no effect on the new token; the owner then uses the new token, and the cancel reports `no_pending_recovery`.

### 10.5 Completion

- Completion runs only when all of these hold, checked inside the queue: a pending record exists; the waiting period has passed; no valid device session exists (D1/D2); and the notice condition of D4 is met (under the strict rule, `notifiedAt` is set; under the wait-only rule, no notice is required).
- Completion rotates the session token, clears the pending record, and records the recovery time. It uses the existing token-rotation path and its rollback.

### 10.6 Failure and rollback

| Failure | Behaviour |
|---|---|
| Pending record cannot be saved | Request refused; nothing changes; error `persistence_failed` |
| Notification send fails (socket closed, or client not reading) | Record stays pending with `notifiedAt` unset. Recovery does not complete while D4 requires a notice. The attempt is counted in logs without key or token values |
| Completion save fails | Token unchanged (existing rollback). Pending record stays. Retry on the next request after the wait |
| Server restarts during the wait | Pending record is in the saved world; the wait continues from `requestedAt` after restart |
| Owner resumes during the wait | Pending record cleared; the current token keeps working |
| Lost response after completion saved | The new token is in the authoritative state but the client never received it. The next key-only presentation after the wait rotates it again (the R7 scenario 2 case). Must be documented for the client team |
| Clock moves backwards | Waiting uses server time from the saved `requestedAt`. A backwards clock can extend the wait but cannot shorten it. This is noted, not solved |

No failure path grants recovery without the wait and the checks above. No failure path deletes a player, a token, or another identity's data.

### 10.7 Existing players and migration

- Existing tokens and existing identities are **unchanged** on deployment. An identity that is online is refused for key-only takeover exactly as today.
- The pending-recovery field is optional in the saved world (absent means none), so files written before the change load without it. This is an additive field and needs a load test on a copy of the saved corpus before rollout (the corpus is not currently available; see `docs/STAGE_28_CAPACITY.md`).
- Old clients keep working for resume. An old client that presents only a key after a pending recovery receives the new pending error. It must be updated to show that state; it cannot be silently given a new session.

### 10.8 Decisions needed before implementation

| ID | Question | Why it matters |
|---|---|---|
| D1 | Confirm: a valid device session = a token presented on a connected socket | Enables the core takeover refusal with no new constants |
| D2 | Should a recently used token (socket closed) also count as valid? If yes, what inactivity window? | Without a window, offline owners are treated as always logged in, so key-only recovery is unreachable |
| D3 | Accept that a lost-device owner is notified only at their next login (no out-of-band channel today)? | This is the real protection level. An attacker can wait out the period silently |
| D4 | Strict rule (recovery completes only after a delivered notice) or wait-only rule (completes after the period, with the attempt recorded)? | Strict rule means no self-service recovery for lost devices. Wait-only rule permits recovery without the owner being notified, which the instruction forbids unless the decision changes |
| D5 | Waiting-period bounds and environment variable name | Default 24 hours is the user proposal; bounds are not set |

**Recommendation for review (not decided):** implement D1 with the live-session rule first; keep key-only recovery for offline identities behind the 24-hour pending period; choose D4 strict for now, so that a lost-device player relies on the break-glass procedure until an out-of-band channel exists (accounts, Option A). Under that choice, self-service recovery of an offline identity is unavailable until a channel exists, and that is a visible product cost.

**Status:** design only. No implementation, client change, schema change, or test has been written for Option B.

## 11. Adopted direction for review (design only; not implemented)

**Status.** Direction adopted for review on 2026-10-10. **No code, client, schema, or test is implemented for this section.** The authentication redesign is not started. Key-only recovery is not removed. Stage 28 remains IN PROGRESS.

### 11.1 The rules

1. **Live session refusal.** A key-only takeover is refused while the identity's device still holds a valid session (section 10.1, D1). This is unchanged in intent.
2. **Verified channel required for self-service.** Self-service recovery of an identity is allowed only when the identity has a **verified notification channel** tied to it (11.2). An identity with no verified channel cannot complete self-service recovery. It goes to operator-assisted recovery (11.5).
3. **Notification before takeover, no silent approval.** A pending recovery is created only if the notice to the verified channel was accepted by the provider. If the notice cannot be sent or accepted, nothing changes and the recovery does not start. Nothing is approved silently on a notification failure.
4. **24-hour wait, cancellable.** Default wait 24 hours from the recorded request time (server time). The owner can cancel during the wait (11.4). The current token keeps working during the wait.
5. **No secrets in records or logs.** Keys, session tokens, cancel tokens, email addresses, and IP addresses are not written to audit records or logs (11.6).
6. **Compatible migration.** Existing identities, tokens, and resume behaviour are unchanged on deployment. The channel is an additive, optional record (11.7).

### 11.2 Smallest viable notification channel: verified email

Options compared:

| Channel | Verdict | Reason |
|---|---|---|
| In-game socket message | Rejected as the only channel | An owner who has lost the device is offline and cannot see it. Section 10.3 shows the gap. |
| Verified email tied to the identity | **Proposed (smallest viable)** | Reaches an offline owner. One provider integration. A verification code proves control of the address. |
| SMS to a verified phone | Possible later | Same proof model, but a telephone provider and number data add cost and a second personal-data class. |
| Social or third-party account | Rejected | Not verified to the identity, and the game has no account system to link it to (Option A). |

**Enrollment.** Only a player who is signed in on the device can add a channel. The flow is: enter an address; the server sends a one-time code to it (stored as a hash, short expiry, rate-limited); the player enters the code; the address is then marked verified with a time. A player who has not enrolled cannot use self-service recovery.

**Delivery and verification.** "Verified" means the address proved control by returning the code. "Delivered" is not claimed: the provider's acceptance is recorded. Provider bounce notices, if configured, mark the channel unusable and stop self-service until the player re-verifies.

### 11.3 What the smallest channel needs

| Area | Change | Notes |
|---|---|---|
| Client | Enrollment screen (address, code); status of channel (none, pending, verified); recovery-pending message; cancel action; message for "operator assistance required" | No client behaviour is invented here. Each screen needs a client test and a UX review. |
| Identity and account | Optional **identity contact** record linked to `playerId`: address (stored with access controls; encryption at rest is a decision, D8), verified time, code hash, code expiry | No account or character columns are added. The contact is one record per identity, in one authoritative store. |
| Database | Additive table for contacts and a recovery-pending record, plus an append-only audit table (11.6). Migration in PostgreSQL. | In the file backend the feature is not available (it is development only). This avoids two sources of truth. |
| Services | Transactional email sender (provider account, API key in the deployment secret store, SPF, DKIM and DMARC for the sending domain); rate limits per identity and per address; cancel endpoint (HTTP POST carrying the one-time token; GET links are avoided because mail scanners often fetch links automatically); operator tooling (11.5) | The sender is an external dependency. Its outage must lead to refusal, not approval. |
| Tests | Fake sender; code expiry and attempts; race between cancel and completion; notice failure leaves nothing changed; audit contains no secret values; existing identities unchanged | Required before implementation (11.8). |

### 11.4 Recovery flow

1. **Request (lost device).** A key-only request for an identity with no live session:
   - no verified channel: refused with `recovery_channel_required` and the operator route (11.5). No takeover.
   - verified channel: a pending record is saved with `requestedAt`, and a notice is sent to the verified address. The notice contains a one-time **cancel token** (random, shown once, stored as a hash, expires at the end of the wait). The notice contains no key, session token, or identity detail beyond what the owner needs.
   - If the notice is not accepted by the provider, the pending record is not kept, and the request is refused with `recovery_notice_failed`. Nothing changes.
2. **Wait (24 hours, default).** The current token keeps working. A second request does not restart the clock (section 10.2, rule 4). A bounded number of re-sends is allowed, and each send is audited.
3. **Cancel.** The owner cancels with (a) the session token on a signed-in device, or (b) the one-time cancel token from the notice. The cancel token proves control of the inbox, which is the second factor a lost-device owner has. A key alone cannot cancel. Cancel is applied inside the serialized queue.
4. **Completion.** After the wait, and only if the pending record still exists, no live session exists, and the channel is still verified: the session token is rotated (existing rotation path and rollback), the pending record is cleared, and a completion notice is sent to the same address. If that notice is not accepted, completion is still recorded (the takeover has happened) and the failure is audited and retried.
5. **Race.** Cancel and completion are serialized. Whichever commits first wins. The loser reports `no_pending_recovery` or `already_cancelled`.

### 11.5 Operator-assisted recovery (lost device, no verified channel)

This is a **written procedure**, not a feature. It is proposed, and it needs review before use.

- **Evidence.** The operator must be satisfied of the owner's identity by an agreed method. The game holds little personal evidence (no accounts), so the method must be defined by the team (for example, characteristics recorded in the saved world that only the owner would know). This is a weak control and is stated as such. **The evidence method is an open decision (D9).**
- **Two people.** One operator requests and a second approves. Both are recorded.
- **Action.** Re-issue the session token (the old one stops working), or remove the live session. No player data is deleted or changed beyond the token.
- **Wait.** Whether the 24-hour wait applies to operator action is an open decision (D10). Until it is decided, operator action is not used for takeover of an identity with a live session.
- **Audit.** Each step is written to the audit table (11.6) with the operator identifier and reason code. No secret values.

### 11.6 Audit (no secrets)

An append-only table with: `occurred_at`, `player_id` (the internal identifier, which the saved world already holds), `event` (one of `contact_added`, `contact_verified`, `contact_removed`, `recovery_requested`, `notice_accepted`, `notice_failed`, `recovery_cancelled`, `recovery_completed`, `recovery_refused`, `operator_reissued`), `actor` (`player`, `system`, or `operator:<id>`), and `reason_code`. It must **not** contain keys, session or cancel tokens, code values, email addresses, IP addresses, names, or free text. A test checks the table's columns and sample rows for these values.

### 11.7 Migration and compatibility

- **Phase 0 (now).** Current behaviour is unchanged. Key-only recovery of an offline identity still works. This is a known risk, and it is recorded here as such.
- **Phase 1.** Enrollment is available and prompted at sign-in (optional). Self-service recovery applies to identities with a verified channel. Other identities keep Phase 0 behaviour during the transition.
- **Phase 2 (requires a separate decision, D7).** Key-only self-service for identities **without** a verified channel is withdrawn, and those players use operator-assisted recovery. This is the change that removes key-only recovery for those identities. It must not start until: enrollment has run for a stated period, a replacement route (11.5) is tested, and the affected players have had notice of the change.
- **Data.** The new tables are additive. Existing saved worlds and PostgreSQL rows are not rewritten. Rollback is to disable the new routes; the tables can stay.

### 11.8 Tests required before implementation

- Live-session refusal (existing behaviour preserved).
- No channel: refusal with `recovery_channel_required`; no state change.
- Notice not accepted: no pending record; no state change.
- Notice accepted: pending record; token unchanged; wait enforced by server time.
- Cancel with session token and with cancel token; key alone refused; expired cancel token refused.
- Cancel versus completion race (both orders).
- Completion when channel is no longer verified: refused.
- Code expiry, attempt limit, and rate limit for enrollment.
- Audit rows contain no secret values (table columns and sample rows checked).
- Existing identities and tokens unchanged after migration; old clients can still resume.
- Saved-world and PostgreSQL migration tested on copies only.

**Notice failure rule (adopted).** If the notice cannot be accepted, recovery does not start, and no silent approval occurs. This is the strict rule of section 10.3 (D4).

### 11.10 What this does not claim

- It does not claim that email proves identity against a determined attacker who controls the inbox. It raises the cost; it does not remove the risk.
- It does not claim delivery to the person. It claims acceptance by a provider.
- It does not claim that operator evidence is strong.
- It does not implement, test, or approve any part of this.
